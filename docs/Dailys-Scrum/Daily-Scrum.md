# Daily Scrum — TechOwl

## Portal de Certificação em Metodologias Ágeis

Este diretório contém os registros oficiais das **Daily Scrums** realizadas pela equipe **TechOwl** durante o desenvolvimento da ABP do **1º semestre de Desenvolvimento de Software Multiplataforma (DSM) — Fatec Jacareí**, referente ao segundo semestre de 2026.

As reuniões seguem os princípios do framework **Scrum** e têm como objetivo acompanhar diariamente a evolução do projeto, identificar impedimentos, alinhar prioridades e registrar decisões que possam impactar o desenvolvimento da solução.

## 📁 Estrutura do diretório

A organização dos documentos seguirá o padrão:

```text
documentos/
└── Daily Scrum/
    ├── README.md
    ├── 2026-09-28.md
    ├── 2026-09-29.md
    ├── 2026-09-30.md
    ├── 2026-10-01.md
    ├── ...
```

Cada arquivo `.md` corresponde ao registro de uma Daily Scrum específica.

### Padrão de nomenclatura

Os arquivos deverão utilizar o seguinte formato:

```text
AAAA-MM-DD.md
```

Exemplo:

```text
2026-10-06.md
```

Esse padrão facilita a organização cronológica dos registros e a navegação pelo histórico do projeto dentro do GitHub.

## 🎯 Objetivo das Daily Scrums

As Daily Scrums são reuniões rápidas de acompanhamento, com duração prevista de aproximadamente **15 minutos**.

Durante cada reunião, a equipe deverá registrar principalmente:

- avanços desde a última Daily;
- atividades planejadas até a próxima reunião;
- impedimentos encontrados;
- decisões tomadas;
- alterações relevantes no Sprint Backlog;
- requisitos funcionais ou tasks relacionados;
- responsáveis pelas próximas ações;
- evidências disponíveis, como links do Figma, diagramas, commits, issues ou documentos.

Discussões técnicas que demandem maior aprofundamento deverão ser tratadas separadamente entre os integrantes envolvidos, evitando transformar a Daily em uma reunião extensa.

## ✅ Regras de registro

Para manter a documentação confiável e rastreável, deverão ser seguidas as seguintes regras:

1. Cada Daily deve possuir seu próprio arquivo `.md`.
2. O registro deve refletir somente informações realmente discutidas ou confirmadas pela equipe.
3. Não devem ser registradas atividades como concluídas sem evidência correspondente.
4. Decisões que afetem requisitos, modelagem, protótipos ou implementação devem indicar o respectivo **RF**, **RNF**, **RP** ou **Task**, quando possível.
5. Alterações importantes no planejamento devem ser registradas também no Sprint Backlog.
6. Caso uma Daily não seja realizada, deverá ser registrado no arquivo correspondente:
   > **Daily não realizada.**

   Sempre que possível, informar também o motivo.
7. Registros antigos que tenham sido inicialmente reconstruídos ou sugeridos deverão ser revisados e validados pela equipe antes de serem considerados atas oficiais.
8. Links, commits, arquivos, protótipos e demais evidências devem ser adicionados ao registro sempre que disponíveis.

## 🔎 Rastreabilidade

Os registros desta pasta fazem parte da documentação do projeto e deverão permitir o acompanhamento histórico das decisões da equipe.

Sempre que possível, as Daily Scrums deverão manter relação com:

- Requisitos Funcionais — **RF**;
- Requisitos Não Funcionais — **RNF**;
- Requisitos do Projeto — **RP**;
- Tasks do Sprint Backlog;
- Protótipos do Figma;
- Modelagem do banco de dados;
- Diagramas;
- Issues;
- Pull Requests;
- Commits;
- documentação técnica.

Essa prática permite identificar quando uma decisão foi tomada, quem ficou responsável por determinada ação e quais artefatos foram impactados.
